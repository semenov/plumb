# Building for wasm-server

`plumb build --target wasm-server app.plumb` compiles a program into a
WebAssembly component for wasm-server (`~/Dev/wasm-server`): it exports
`wasi:http/incoming-handler` and imports what it uses of `platform:sdk`.

How it fits together:

- `cgen.rs` (`generate_wasm`) pastes `runtime/wasi.h` (what WASI lacks:
  processes, signals, terminals fail with ENOSYS), the bindings header
  and the runtime as usual, then `runtime/http_wasm.h` instead of the
  socket server and `runtime/db_wasm.h` instead of SQLite. The program
  gets `lt_program_main` instead of C's `main`.
- `main.rs` (`compile_wasm`) compiles that with wasi-sdk's clang for
  `wasm32-wasip2` as a reactor, with `runtime/wasm/guest.c` and
  `guest_component_type.o`; clang's linker turns it into a component.
- The host calls `handle` once per instance; it runs `main`, whose
  `http.serve` answers the request.

## The bindings

`runtime/wasm/guest.{c,h}` and `guest_component_type.o` are generated by
wit-bindgen 0.62 from `wit/` and checked in, so building needs only
wasi-sdk. `wit/deps/platform-sdk` is a copy of wasm-server's `wit/`; after
it changes there:

```sh
cp ~/Dev/wasm-server/wit/*.wit wit/deps/platform-sdk/
wit-bindgen c wit --world plumb:wasm-server/guest --out-dir ../src/runtime/wasm
```

A component imports only the interfaces the program calls, so adding an
interface to the world costs programs that don't use it nothing.
